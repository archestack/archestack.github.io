How the ranking works

Every project gets a score out of 100 from public signals with published weights. The score sets the order; the review explains the project.

Signals and weights

A signal we cannot measure yet is left out and its weight goes to the others, so no project loses points for something we have not checked.

Where the data comes from

  • Projects are found in curated lists, app stores and template galleries, then fact-checked on GitHub: stars, last commit, license, Docker files.
  • Each review is written from the project's own README and never copied from other lists: what it does, what it needs, and strengths and weaknesses you can check.
  • Reviews are rewritten when the README or the latest release changes. Projects with no commits for 12 months are marked stale, and archived ones drop off.
  • A project's own claim, such as "an alternative to Cursor" in its README, is labelled as its claim.

Health facts

Each project page has a Health box. Nothing in it changes the score.

  • Releases: GitHub releases in the last 12 months, pre-releases left out, and the days since the latest one.
  • Top contributor: the share of the last 52 weeks of commits on the default branch made by one person, from GitHub's contributor stats. Bots and coding-agent accounts such as Claude and Codex are left out. A high share means the project leans on one person.
  • Security advisories: the project's own published GitHub security advisories from the last 12 months, and how many GitHub rates critical or high. Publishing advisories is good practice, so the count alone says little.
  • Package advisories: when the repo's root manifest names a package on npm, PyPI, crates.io or Go, and deps.dev links that package back to the repo, the known advisories (from OSV) for its latest version.
  • OpenSSF Scorecard: the score from OpenSSF's public Scorecard API, which covers only some repos.

Releases update at every refresh; the other facts are read again about every two days. A fact we could not read says "Not checked".

Safety checks

MCP servers and skills, rules and plugins have a Safety checks section on their project page: up to 14 checks, each one pass, fail or N/A, with a link to the file line or registry page we read it from. The summary reads "Checks passed: 12 of 13" with the date. A check that does not apply drops out of the count. Nothing here changes the score.

The format follows the OpenSSF Scorecard (opens in a new tab): each check has a name and a rule and lists its limits, with no overall grade. The checks themselves come from Scorecard, Anthropic's guidance on skills for enterprise (opens in a new tab) and the issue codes of Snyk's agent scanner.

Next to the checks the page lists facts that are neither pass nor fail: whether the project bundles scripts, hooks, a bin folder or an MCP config file, whether it calls other MCP tools, and the domains its agent files link to. Any of them can be fine, and you decide what matters for your setup.

How the results are read

We read public data only: the files on the default branch (with gitleaks, OpenSSF Scorecard and osv-scanner), npm, PyPI, the official MCP Registry, deps.dev, OSV and the repo's own GitHub advisories. We never run a project's code. We run the checks once a week, so a fix in the repo shows up at the next read.

What we cannot check

  • What an MCP server's tools say once it runs. Tool descriptions built at runtime, and tools that change after you install them, need the live server.
  • Private alerts. Only maintainers see Dependabot and code-scanning alerts.
  • What the code does: network traffic, system calls, content a skill downloads when it runs, or whether a vulnerable function is ever called.
  • Tool annotations such as read-only. The MCP spec says clients must not trust them, so we do not show them as permissions.

When a result is wrong

Each list has a "Safety check is wrong" form on GitHub. A person reads every report. When a check was wrong, the project page shows the correction and its reason next to the check.

Independence

Nobody can pay for a place. Sponsors, affiliate links and tips, if any, are labelled and never touch the order. Archestack sells none of the tools it lists.

Hiring has no say in the order either. Teams behind the stack lists open roles at the teams that build listed projects; a team with open roles ranks the same as one without.

Corrections and opt-outs

Every list has forms on GitHub to add a project, fix a wrong fact or opt out (handled within 24 hours): Best of Vibe Coding (opens in a new tab) or Best of Open-Source AI (opens in a new tab). You can reuse all the data under CC BY 4.0 from data.json, the API or the YAML in each list's data folder on GitHub: best-of-vibe-coding/data (opens in a new tab), best-of-ai/data (opens in a new tab).
